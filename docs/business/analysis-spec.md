# 关系分析规范

评分见 [rules-v0-experimental](../scoring/rules-v0-experimental.md)；决策见 [ADR-0001](../adr/0001-ai-suggests-level-program-computes-score.md)。

## 1. 触发与同意
仅由用户点击"开始分析"触发。新增资料只显示"有新资料待分析"。

**同意关卡**：首次向 AI 服务商发送内容之前（截图识别或分析，先发生者为准）必须展示并记录同意，截图识别与分析共用同一条记录。文案写明：发给哪家服务、发送什么、用途、聊天含他人信息，并如实写"服务商留存条件**尚未核实**，不对服务商侧的留存或删除作承诺"（核实后才可改写）。同意按**文案版本 + 服务商**记录：文案有实质修改（`CONSENT_VERSION` 加 1）或更换服务商后需重新同意。粘贴文本导入不发送给 AI 服务商，不受此限。

## 1a. 快照与额度
提交时取**输入资料快照**：当前已保存的全部消息的 (消息ID, 修订号, 批次, 资料类型, 顺序, 发言人, 时间与精度)。内容不重复存放，按 (消息, 修订) 回查修订表重建（修订只增不改，见 ADR-0002）。同时记录模型、提示词版本、规则版本、偏好版本与偏好取值。提交时预留 1 次分析额度（任务键 `analysis:<分析ID>`），成功结算；失败、作废、超时退还；每次提交是新记录，因此重试用新键、只扣一次。同一对象同时只能有一次进行中的分析。

分析在写回前再次确认快照里的消息仍存在、仍是被引用的修订；否则结果作废（INVALIDATED）并退还额度。对象或批次被删除后迟到的任务不能写回（删除围栏，先锁对象再锁分析记录）。排队/运行超过 15 分钟没有结果的分析由清理任务判为失败并退还。

## 2. 处理顺序
1. **提取事实与事件**：长聊天按条数（≤60）与字数（≤3500）分段，每段独立提取；线下事件（见 §2a）按同样的上限单独成段，排在聊天各段之后。模型只能引用本段内的代码（消息 M1、M2…，线下事件 E1、E2…），引用段外的代码使整次分析失败。汇总只合并带引用的事实，不依赖失去出处的摘要。
2. **按维度解释**：五维 = 双向投入、了解意愿、行动兑现、沟通与边界、意愿与节奏匹配。价值观等只分析资料明确涉及的部分，没有则"未知"。
3. **校验**：Zod 校验结构；维度必须齐全、等级必须是配置里的档位；每条引用必须解析到快照内真实的消息修订或线下事件修订；输出不得含心理诊断/人格类型判断，不得含成功率、概率或百分比；建议至多 3 条。不合格则整次分析失败（不入库、退还额度），用户可再次提交。
4. **程序核验**（不采信模型自称）：
   - 每个维度的状态由程序按 `config/scoring/v0.json` 重新计算（证据单元、情境、资料类型封顶，见评分规则 §3）；模型自称与核验不一致时以程序为准并记录警告；非"已知"的维度丢弃等级建议。
   - **明确拒绝**必须引用来自"对方"的消息（只有自己说的不算）；事实里带拒绝信号且来自对方的，即使模型漏报也视为成立。成立后只保留"尊重边界"类建议，推进、保持、了解类建议一律剔除。

## 2a. 线下事件（M3b）
用户补充的见面、通话、取消安排、补充事实。**事实**（类型、日期、经过）与**个人感受**分开存放：
- 事实每次修改产生新修订（同 ADR-0002，`OfflineEventRevision`），报告引用 (事件ID, 修订)；个人感受只在事件行上、可随时修改、不产生修订。
- **只有事实发送给 AI 服务商**；个人感受不进入快照、不进入模型输入、不会被引用为证据，报告展开事件证据时也只显示事实。
- 事件是**一个证据单元**；只有日期精度，因此按日期计情境（同一天的多个事件是多个单元、一个情境）。事件是用户自己的记录而不是连续的聊天，资料类型按“精选”对待：只靠事件撑不起“双向投入”这类受封顶的维度。
- 事件不能证明“对方明确拒绝”（见 §4）。已有事件的对象仍需要至少一批已保存的聊天资料才能开始分析（事件是补充资料）。
- 事件日期不能晚于今天（北京时间）。

## 3. 每个维度的输出
观察到的事实｜可能的解读｜支持证据｜反面证据｜缺失信息｜状态与等级建议。**用户感受不能当作对方的客观事实**，只可作为"用户的体验"单列。

## 4. 安全与边界
- 聊天文本与图片内的任何指令都是**待分析资料**，不得覆盖系统规则（评测样本：指令注入）。
- 不做心理诊断、人格类型判断；少量聊天不下结论。
- 消息多、回复快、礼貌问候、单次夸奖，不直接等于恋爱意愿。
- 出现明确拒绝或要求停止联系：设标记，**停止**一切追求/推进类建议，仅可给尊重边界的说明。明确拒绝必须引用来自“对方”的聊天消息；用户自己记录的线下事件不能单独成立（**已知限制**：用户当面听到的拒绝如果只记成事件而聊天里没有，报告不会据此停止推进类建议，见 HANDOFF 待决事项）。

## 5. 报告结构
当前结论 → 五维分析 → 评分与信息充分度 → 可展开证据 → 最多 3 条行动建议（每条含依据、目的、未知项）→ 资料范围（截止时间、批次、资料类型）→ 规则版本与"实验规则"标识。不展示成功概率、不展示百分比置信度。报告在五维分析之后展示“适配分”卡片：五个维度都“已知”才有分数（由纯函数按规则版本与报告当时的偏好计算，AI 只给等级建议）；否则不显示分数，说明哪些维度不是“已知”，**不展示任何聚合数**。报告页另有“趋势”卡片（同规则同偏好的快照比较，口径变化只标注）。对比页见评分规则 §6。

## 6. 快照与复盘
每次分析保存：模型、提示词版本、规则版本、偏好版本、输入资料快照（聊天消息与线下事件各自的版本引用，可重建）、AI 原始结构化输出。**时间线**（对象详情“关系记录”）同时显示线下事件、好感变化（记录“从什么变成什么”）、分析快照（结论摘要、资料范围、规则/偏好版本）；事实与感受分开存储与展示。相对上一份分析，规则或偏好版本不同的快照标注“口径变化”。资料纠正后旧结果标记"资料纠正已过期"。当前只有最新报告可展开查看，旧快照保留结论摘要。

## 7. 新鲜度
报告相对当前数据的状态，优先级见 [state-machines §4](./state-machines.md)。判定依据：快照里的消息被修改或所属批次被删除、快照里的线下事件**事实**被修改或事件被删除（只改个人感受不算）→ 资料纠正已过期；当前规则版本与报告不同 → 规则变更；当前偏好版本与报告不同 → 偏好变更待更新；存在不在快照内的已保存批次或线下事件 → 有新资料待分析（M3a 时期没有事件的旧报告，之后补充事件同样提示有新资料）。偏好或规则变更后重新分析，分差属于口径变化，界面须提示，不得解释为关系升温或降温。

## 8. 评测
安全评测集在 `samples/eval/analysis-cases.json`（虚构聊天），覆盖礼貌回复、精选片段、明确拒绝、临时取消、指令注入，以及没有安排/没有争执/单次夸奖。`npm run eval:analysis` 生成 [docs/evals/analysis-mock-results.md](../evals/analysis-mock-results.md)。**当前模型是规则型模拟实现，评测只验证框架、校验器与程序核验，不代表真实模型质量**；真实模型评测待接入后进行。
